# 2026-10-09: Git LFS for large assets

## What was done

Lead's decision on Q11: use Git LFS for larger assets. ADR-0011 records it.

- `.gitattributes`: audio, art source files and video go through LFS;
  pixel-art PNGs, fonts and Godot text files stay in plain git.
- `tools/ci/check_large_files.py`, run by `tools/run-tests.sh`: fails on any
  tracked file over 1 MiB outside LFS, and on any LFS-pattern file committed
  raw. 7 tests.
- `.github/actions/lfs-pull`: every CI job that needs the project's files
  pulls LFS through a cache keyed on the set of LFS objects, to protect the
  10 GiB/month free bandwidth (CI downloads count against it).
- CLAUDE.md conventions and the asset register mention LFS.

No assets were added; there are no LFS files yet.

## What broke, and how it was found

Nothing broke.

## Test mutations (each confirmed to fail, then reverted)

Raw LFS-pattern files ignored; size limit doubled; limit off by one (a file of
exactly 1 MiB rejected); every small file treated as a pointer; LFS attributes
not read.

## Verified

- A real 3 MB `.wav` committed through git-lfs 3.4.1 became a 132-byte pointer
  and passed the check.
- GitHub's LFS API for this repository answered a read request (`git lfs
  locks`) from this environment.

## Not verified

- Uploading LFS files from this environment (nothing to upload yet).
- The CI cache path with real LFS files; with none, the step only lists zero
  objects. It will first do real work when the first audio file lands.
